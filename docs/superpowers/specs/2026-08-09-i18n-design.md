# Internationalization — Design Spec

**Date:** 2026-08-09
**Status:** Approved, ready for implementation planning

## Overview

Make MoneyTrack multilingual with [next-intl](https://next-intl.dev), in
English, Brazilian Portuguese, and German. The locale lives in the URL as the
first segment (`/en-US/dashboard`), and every user-facing string — page copy,
validation messages, and auth error messages — comes from a message catalog
rather than a literal in a component.

This is the first feature to touch every route in the app: all of `src/app/`
moves under a `[locale]` segment, and that layout becomes the root layout.

## Goals

- Three locales: `en-US`, `pt-BR`, `de-DE`, addressed by BCP 47 tag.
- The locale is the first path segment on every in-app URL.
- Locale resolution order: URL prefix → `NEXT_LOCALE` cookie → `Accept-Language`
  → `en-US`.
- Every string currently rendered to a user is translated in all three locales,
  including zod validation messages and better-auth error messages.
- Internal navigation stays locale-relative without any call site passing a
  locale explicitly.
- `<html lang>` reflects the active locale.
- The existing test suites pass, plus new coverage for negotiation and for
  catalog completeness.

## Non-Goals

Each is its own piece of work.

- **A locale switcher UI.** Detection and the cookie *read* ship here; the
  control that writes the cookie comes later. This was an explicit scoping
  decision, not an oversight.
- **Number, date, and currency formatting.** next-intl's `useFormatter` comes
  free with this setup, but nothing currently on screen needs it — the
  dashboard is a placeholder. The `currency`, `numberFormat`, and `dateFormat`
  fields already on the user model are for that later feature.
- **Translated pathnames.** Routes stay English (`/pt-BR/dashboard`, not
  `/pt-BR/painel`). next-intl can add a `pathnames` map later without a
  migration.
- **A `locale` column on `User`.** The cookie is the only persistence.
- **Translated emails.** No email provider is configured.
- **Right-to-left support.** None of the three locales need it.

## Decisions

Settled during design. Recorded with reasoning so they are not relitigated
mid-implementation.

### Locale tags all carry a region

`en-US`, `pt-BR`, `de-DE`. `de` alone would be defensible — German has no
regional split that matters to this app — but a uniform tag shape keeps every
URL, filename, and catalog key the same shape, and removes the recurring
question of which locales get a region and which do not.

### zod schemas become factories that take a translator

`.claude/rules/validation.md` requires one schema shared by the browser and the
server, and treats messages as user-facing copy. Translation puts those two in
tension: a module-level constant cannot hold a string that depends on the
request.

Schemas become functions taking a translator:

```ts
export const createLoginSchema = (t: AuthValidationTranslator) =>
  z.object({
    email: z
      .string()
      .trim()
      .min(1, t("email.required"))
      .pipe(z.email(t("email.invalid")))
      .transform((value) => value.toLowerCase()),
    password: z.string().min(1, t("password.required")),
  });
```

The alternative — schemas emitting bare message keys, translated at each render
site — was rejected. It keeps the schema simpler at the cost of pushing a
`t()` call into every component that renders an error, where forgetting one
ships `email.required` to a user. It would also put a raw key in the `APIError`
message thrown by the sign-up hook, and in every log line.

With factories, a message is a real sentence everywhere it appears: in
react-hook-form, in API responses, in logs.

The shared-schema rule is preserved exactly — the *same factory* runs on both
sides.

### Bounds are interpolated, not baked into copy

```json
"name": { "tooLong": "Name must be at most {max} characters." }
```

`MAX_NAME_LENGTH` stays the single source of truth and is passed in at call
time. Three catalogs each hard-coding `60` is three places to forget.

### better-auth errors are translated on the client, from the code

The endpoint is `src/app/api/auth/[...all]/route.ts` — deliberately *outside*
the `[locale]` segment, so no locale is resolved there. Translating in the hook
would mean hand-rolling locale negotiation from `ctx.request`, duplicating what
next-intl's middleware already does correctly.

So the server side is unchanged: the `before` hook keeps throwing a stable
`code` with an English `message`. The code is the contract; the message is for
logs and non-browser clients. The client translates:

```ts
const t = useTranslations("errors.auth");
setFormError(authErrorMessage(t, error.code));
```

This yields one source of truth per message — the catalog — and zero locale
plumbing inside better-auth. The cost is that a direct API consumer receives
English prose alongside the code it should actually be reading.

The same applies to `AuthErrorDialog`, which maps `?error=` slugs from
better-auth's `onAPIError.errorURL` redirect. Those slugs are already stable
identifiers; they become catalog keys.

### The server can still translate when it needs to

`createTranslator` from next-intl works outside React and outside a request
scope. `src/lib/auth.ts` uses it to build the server-side payload schema with
the English catalog:

```ts
const t = createTranslator({
  locale: "en-US",
  messages: enUS,
  namespace: "validation.auth",
});

export const signUpPayloadSchema = createSignUpPayloadSchema(t);
```

Future Server Actions inside `[locale]` use `getTranslations()` instead, which
resolves the request's locale. The infrastructure is there when it is needed;
better-auth simply does not need it.

### The locale cookie is pinned, not inherited

`localeCookie: { name: "NEXT_LOCALE", maxAge: 60 * 60 * 24 * 365 }`.

next-intl's default happens to be `NEXT_LOCALE`, but the cookie name is about
to become part of this app's own contract — a switcher will write it. Pinning
it means an upgrade cannot silently move it.

### `localePrefix: "always"`

Every URL carries its locale. `/` redirects to `/{negotiated}`. This makes the
URL fully self-describing: a shared or bookmarked link renders identically for
everyone, and no route has two addresses.

A pathname whose first segment is not a known locale is prefixed and then 404s
— `/fr/dashboard` becomes `/en-US/fr/dashboard`, not found. An unsupported
locale fails visibly instead of being silently coerced to English.

### Route pathnames stay English

See Non-Goals. Worth stating positively: `/pt-BR/dashboard` is correct and
intentional, not an unfinished translation.

## Architecture

### Configuration

```
src/i18n/routing.ts      defineRouting — locales, default, prefix, cookie
src/i18n/request.ts      getRequestConfig — resolves locale + loads messages
src/i18n/navigation.ts   createNavigation — Link, redirect, useRouter, usePathname
```

`routing.ts` is the single source of truth for the locale list. Nothing else
hard-codes it.

`next.config.ts` wraps the config in `createNextIntlPlugin()`.

Next.js 16.3 provides `next/root-params`, which next-intl uses to resolve the
locale in `request.ts`. Static rendering therefore works without
`setRequestLocale`, which next-intl now documents as legacy.

### File layout

```
messages/
  en-US.json          reference catalog
  pt-BR.json
  de-DE.json

src/app/
  [locale]/
    layout.tsx        ← the root layout: <html lang>, fonts, globals.css,
                        NextIntlClientProvider, generateMetadata,
                        generateStaticParams
    loading.tsx
    not-found.tsx
    page.tsx          redirect("/dashboard") via next-intl's redirect
    (auth)/
      layout.tsx
      login/page.tsx
      register/page.tsx
    dashboard/
      layout.tsx
      loading.tsx
      page.tsx
  not-found.tsx       ← owns its own <html>; catches paths the proxy matcher
                        skips (dotted paths such as a missing /favicon.ico),
                        which have no [locale] layout above them
  api/auth/[...all]/route.ts    unchanged, outside [locale]
  globals.css
```

`src/app/[locale]/layout.tsx` becoming the root layout is the documented
pattern; there is no `src/app/layout.tsx` afterwards.

### Proxy

`src/proxy.ts` composes locale routing with the existing auth gate, in that
order:

1. Run next-intl's middleware. If it returns a redirect — the path had no
   locale prefix — return it unchanged.
2. Otherwise strip the locale prefix and test the remainder against
   `PROTECTED_PATHS` (`["/dashboard"]` today).
3. If protected and `getSessionCookie(request)` is absent, redirect to
   `/{locale}/login`.
4. Otherwise return next-intl's response, preserving the headers and cookie it
   set.

Step 4 matters: returning a bare `NextResponse.next()` would discard the locale
cookie and the `x-next-intl-locale` header the middleware attaches.

The matcher widens from `/dashboard` to:

```ts
matcher: ["/((?!api|_next|_vercel|.*\\..*).*)"]
```

`api` is excluded so better-auth's endpoint is never touched by locale routing.

The existing comment on the auth check stays accurate and stays in place: this
is not a security boundary, only an optimization, and
`auth.api.getSession()` in `dashboard/page.tsx` remains authoritative.

### Message catalog

One JSON file per locale, namespaced by area:

```json
{
  "metadata": { "title": "…", "description": "…" },
  "common": { "appName": "MoneyTrack", "loading": "Loading…", "or": "or" },
  "auth": {
    "login": { … },
    "register": { … },
    "google": { … },
    "signOut": { … },
    "errorDialog": { "account_not_linked": { "title": "…", "description": "…" }, … }
  },
  "dashboard": { … },
  "validation": { "auth": { "email": { … }, "name": { … }, "password": { … } } },
  "errors": { "auth": { "INVALID_EMAIL_OR_PASSWORD": "…", "fallback": "…" } },
  "ui": { "passwordInput": { … }, "sidebar": { … }, "sheet": { … } }
}
```

`en-US.json` is the reference. A `global.d.ts` augments next-intl's `AppConfig`
with `Locale` and `Messages: typeof import("../messages/en-US.json")`, so every
`t("…")` key is checked at compile time against English.

TypeScript checks keys against English only, so a key missing from `pt-BR.json`
or `de-DE.json` compiles fine. A unit test asserting all three files have
identical key sets is what actually catches that — see Testing.

### Client components

`NextIntlClientProvider` sits in `src/app/[locale]/layout.tsx` and passes the
whole catalog. The catalog is small and almost all of it is auth copy rendered
by client components; selectively picking namespaces would be machinery
without a payoff. Revisit if the catalog grows large.

### Navigation

`src/i18n/navigation.ts` re-exports locale-aware `Link`, `redirect`,
`useRouter`, `usePathname`, and `getPathname`.

- `AppLink` wraps next-intl's `Link` instead of `next/link`. `useLinkStatus`
  still works, because next-intl's `Link` renders a `next/link` underneath —
  so `PendingOverlay` is unchanged.
- The sidebar's plain `next/link` becomes next-intl's plain `Link`. The
  reasoning in `navigation-loading.md` is unaffected: still no `AppLink`
  inside the shell, still covered by the segment's `loading.tsx`.
- `router.replace("/dashboard")` in `LoginForm`, `RegisterForm`, and
  `SignOutButton`, `router.replace("/login")` in `AuthErrorDialog`, and the
  `redirect()` calls in `page.tsx`, `login/page.tsx`, `register/page.tsx`, and
  `dashboard/page.tsx` all switch to the `@/i18n/navigation` versions. Every
  one of them keeps its existing English path and becomes locale-relative
  automatically.
- `authClient.signIn.social`'s `callbackURL` and `errorCallbackURL` are
  strings handed to Google and to better-auth, not to the router, so
  locale-aware navigation cannot rewrite them. `GoogleButton` reads
  `useLocale()` and builds them explicitly — `` `/${locale}/dashboard` `` and
  `` `/${locale}/login` `` — and this is the one place a locale is passed by
  hand, so it needs a comment saying why.

  `onAPIError.errorURL` in `src/lib/auth.ts` has the same problem and no
  request context to solve it with: it is static configuration. It stays
  `/login` and relies on the proxy to redirect to the negotiated locale.
  Because `errorCallbackURL` covers the OAuth failures the user actually hits,
  this only affects failures that bypass the client entirely — where one extra
  redirect is acceptable.

### Translation inventory

Everything below currently holds a literal string and moves to the catalog.

| File | Strings |
| --- | --- |
| `app/[locale]/layout.tsx` | metadata title and description (currently the create-next-app defaults — replaced with real copy) |
| `(auth)/login/page.tsx` | heading, description, "or", "Don't have an account?", "Sign up" |
| `(auth)/register/page.tsx` | heading, description, "or", "Already have an account?", "Sign in" |
| `dashboard/page.tsx` | "Signed in ({name})", placeholder paragraph |
| `dashboard/layout.tsx` | "MoneyTrack", "Dashboard" label and tooltip |
| `dashboard/loading.tsx` | "Loading…" (sr-only) |
| `auth/login-form.tsx` | field labels, placeholders, "Sign in" / "Signing in…" |
| `auth/register-form.tsx` | field labels, placeholders, submit and pending labels |
| `auth/google-button.tsx` | "Continue with Google" / "Redirecting to Google…" |
| `auth/sign-out-button.tsx` | "Sign out" / "Signing out…" |
| `auth/auth-error-dialog.tsx` | two slug entries plus fallback, "Got it" |
| `ui/password-input.tsx` | "Show password" / "Hide password" |
| `ui/fullscreen-loader.tsx` | default `label` — becomes a catalog lookup rather than a default parameter |
| `ui/sidebar.tsx` | "Toggle Sidebar" (×3), "Sidebar", "Displays the mobile sidebar." |
| `ui/sheet.tsx` | "Close" |
| `lib/validations/auth.ts` | all zod messages |
| `lib/auth-errors.ts` | all eight code messages plus the fallback |

`sidebar.tsx` and `sheet.tsx` are vendored shadcn components. Translating them
means they will diverge from upstream; that is accepted, since an untranslated
`aria-label` is a real accessibility gap for a screen-reader user browsing in
German.

`FullscreenLoader` is rendered from both a Server Component (`loading.tsx`) and
a Client Component (`AppLink`'s portal). next-intl's `useTranslations` works in
both, so a single implementation covers it.

## Testing

### Unit (Vitest)

- **Schema factories** are called with a key-echoing stub, `(key) => key`, and
  assertions are on keys rather than English prose. Coverage is otherwise
  unchanged from `auth.spec.ts`: every rule, both sides of every boundary,
  normalization, and the cross-field guard. Decoupling these from copy means a
  wording change is not a test failure.
- **`authErrorMessage`** is tested the same way, including that an unrecognized
  code returns the fallback rather than letting `t()` throw on a missing key.
- **Catalog parity**: a new spec loads all three JSON files, flattens them to
  dotted key paths, and asserts the sets are identical. This is the only thing
  standing between a forgotten German string and production.
- **Component specs** wrap `render` in `NextIntlClientProvider` with the real
  `en-US` catalog. Their existing English assertions keep passing unchanged, so
  the actual copy stays verified end to end rather than only its keys. A small
  `renderWithIntl` helper avoids repeating the wrapper in six files.

### End-to-end (Playwright)

- A URL helper builds locale-prefixed paths; existing specs default to `en-US`
  and are otherwise untouched in intent.
- `global-setup.ts` and `helpers.ts` are updated for the prefixed URLs.
- New negotiation coverage:
  - `/dashboard` with no cookie and `Accept-Language: pt-BR` lands on
    `/pt-BR/login`.
  - A `NEXT_LOCALE=de-DE` cookie beats a `pt-BR` header.
  - Neither cookie nor a supported header gives `en-US`.
  - `/fr/dashboard` returns 404.
  - The login page renders German copy under `/de-DE/login`.
- The direct-POST bypass test in `registration.spec.ts` is unchanged in
  substance: it asserts the error **code**, which this feature does not touch.

## Documentation

Two rule files contain code examples that this makes wrong, and both are
updated in the same work:

- `.claude/rules/validation.md` — the schema example becomes a factory, and the
  section on library-owned endpoints gains the `createTranslator` pattern and
  the "codes are the contract" rule.
- `.claude/rules/navigation-loading.md` — `AppLink` and the sidebar link now
  come from `@/i18n/navigation`.

A new `.claude/rules/i18n.md` records the standing rules for adding copy: never
a literal in a component, `en-US.json` is the reference, add the key to all
three files in the same commit, bounds are interpolated.

## Risks

- **Every route moves.** The change is wide but mechanical. The e2e suite is
  the safety net, and it must be green before this is considered done.
- **The root layout relocates.** `src/app/[locale]/layout.tsx` becoming the root
  layout is the documented pattern, but the paths the proxy matcher excludes
  have no layout above them, which is why `src/app/not-found.tsx` carries its
  own `<html>`.
- **Translation quality.** The pt-BR and de-DE copy is written by Claude. The
  Portuguese is high confidence. The German is competent but should get a
  native read before shipping — particularly the password-composition message
  and the auth error dialog, where tone matters more than literal accuracy.
  This is a review task, not an implementation blocker.
