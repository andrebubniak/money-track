# Internationalization Guideline

How copy works across MoneyTrack. Applies to every string a user can read —
including `aria-label`, `title`, `tooltip`, and `sr-only` text.

## Never write a user-readable string in a component

Copy lives in `messages/<locale>.json`. A literal in a component is a string
that exists in exactly one language, and nothing will ever tell you it is
missing from the other two.

```tsx
const t = useTranslations("auth.login");
<Button>{t("submit")}</Button>
```

`useTranslations` works in both Server and Client Components. On the server you
can also use `getTranslations`, which is async and required in an `async`
component.

## `en-US` is the reference; all three change together

`messages/en-US.json` is what TypeScript checks `t("…")` keys against — the
augmentation lives in `global.d.ts`. `pt-BR.json` and `de-DE.json` are checked
only by `src/i18n/messages.spec.ts`, which asserts identical key sets,
identical `{placeholders}`, and no empty strings.

So: **add a key to all three files in the same commit.** The compiler will not
catch a missing German string. The test will.

The three locales are `en-US`, `pt-BR`, `de-DE`, declared in
`src/i18n/routing.ts`. Nothing else hard-codes that list.

## Interpolate numbers, never write them into copy

```json
"tooLong": "Name must be at most {max} characters."
```

```ts
t("name.tooLong", { max: MAX_NAME_LENGTH })
```

A `60` written into three catalogs is three places to forget when the bound
changes.

That is the `validation.auth` pattern: the caller passes the value at the
call site, so a message that needs one and doesn't get one is a TypeScript
error. `errors.auth` messages fill their placeholders a different way — see
"Validation and error messages" below.

## Navigate with `@/i18n/navigation`

`Link`, `redirect`, `useRouter`, `usePathname`, and `getPathname` come from
`@/i18n/navigation`, not from `next/link` or `next/navigation`. Call sites keep
their English path — `href="/dashboard"` — and the active locale is added
automatically. See `.claude/rules/navigation-loading.md`.

There are two kinds of exception. One is a URL handed to a third party:
`callbackURL` and `errorCallbackURL` in `GoogleButton` are sent to Google and
to better-auth, so they are built by hand from `useLocale()`. The other is
code that runs before `[locale]` exists to read: `src/proxy.ts` writes
`` `/${locale}/login` `` itself when redirecting a signed-out visitor, because
middleware runs ahead of the app router and has no access to
`@/i18n/navigation`'s `redirect` — it works out the locale from the URL with
its own `splitLocale` helper instead. Those three are the only places in the
app where a locale is written into a path manually.

## An unsupported locale in the URL is coerced, not 404ed

`/abc/dashboard` and `/fr/dashboard` both redirect to `/en-US/dashboard` — or
to whatever `NEXT_LOCALE` and `Accept-Language` resolve to. `src/proxy.ts`
strips a leading segment that `src/i18n/locale-segment.ts` judges to be shaped
like a language tag but is not one of ours, then lets next-intl prefix what is
left.

Two things this deliberately does **not** do:

- **Invent a region.** `/de` is not coerced to `/de-DE`; it falls back like any
  other unknown tag. Guessing that `/pt` means `pt-BR` rather than `pt-PT` is
  not a guess worth making.
- **Touch anything but the locale segment.** `/en-US/nonexistent` still 404s.

Casing is handled by next-intl itself — `/en-us/dashboard` redirects to
`/en-US/dashboard`. That redirect is next-intl's own doing, but it only gets
the chance because `stripUnknownLocale` deliberately leaves a mis-cased
*supported* locale in place instead of stripping it — the case-insensitive
comparison at `src/i18n/locale-segment.ts` (`locale.toLowerCase() === first.toLowerCase()`)
is the code of ours that makes it reachable. `/pt-br` is the case that carries
the weight: stripping it would fall back to `en-US` and silently discard the
user's requested Portuguese. `/en-us` would coincidentally still land on
`en-US` either way, so it does not prove much on its own. `src/proxy.spec.ts`
pins the redirect so an upgrade cannot drop it quietly.

**A new top-level route may not begin with a two- or three-letter
hyphen-delimited part.** Not just a short route name like `/faq` — `/tx-import`,
`/co-owners`, and `/faq-page` all match the shape too, because only the first
part before a hyphen is checked. The guard test in
`src/i18n/locale-segment.spec.ts` fails if one is ever added; rename the route
rather than widening the regex.

## Changing locale

`src/components/nav/locale-switcher.tsx` sits in the sidebar footer beside the
sign-out button. It calls `router.replace(pathname, { locale })` — `pathname`
from `@/i18n/navigation` is already locale-free, so it is the same page in
another language.

It writes no cookie. next-intl's client router calls `syncLocaleCookie` on a
locale switch, and the middleware ignores non-`document` requests so a prefetch
cannot clobber a fresh choice. Do not add cookie handling here.

The trigger disables itself while the switch is in flight, via `useTransition`.
A locale switch changes the `[locale]` segment itself, and `src/app/` has no
`loading.tsx`, so no route-level Suspense fallback is guaranteed to cover it —
without the pending state the click could produce no visible response at all
while the new page is fetched and the session re-read. Do not reach for a
full-screen overlay here instead; it would blank the sidebar. See
`.claude/rules/navigation-loading.md`.

Language names are endonyms — "Português (Brasil)", not "Portuguese (Brazil)" —
so `nav.localeSwitcher.locales.*` holds identical values in all three catalogs.
Only `nav.localeSwitcher.label` is translated.

## Server Components read the locale with `getLocale()`, not `params`

Every page under `src/app/[locale]/` that needs the active locale — to pass
`redirect()`'s explicit `locale` argument, or to build a path by hand — calls
`await getLocale()` from `next-intl/server`, not `await params`. Do the same
in a new page.

The `[locale]` segment is already validated once, in the root layout
(`hasLocale`/`notFound` in `src/app/[locale]/layout.tsx`) and again in
`src/i18n/request.ts` for the request config. Reading `params` and
re-narrowing it per page would only duplicate that guard clause — this
already happened once and had to be pulled back out.

## A Server Action is handed its locale; it cannot find one

`getLocale()` and a bare `getTranslations("…")` **throw** inside a Server
Action. Both resolve through `src/i18n/request.ts`, which reads
`next/root-params` — and root params only exist while rendering a route, so
Next raises "`import('next/root-params').locale()` was used inside a Server
Action" and the action dies with it.

So every action in `src/lib/actions/` takes the active `locale` as its last
argument and passes it to `getTranslations({ locale, namespace })`, which
skips the lookup. The caller is a Client Component, where `useLocale()` is
correct and cheap. Validate what arrives — it comes off a POST body like any
other argument — with `hasLocale`, falling back to `routing.defaultLocale`.

Do **not** substitute the `NEXT_LOCALE` cookie for that argument. next-intl
only writes it when an existing cookie is outdated, or when there is none
*and* Accept-Language disagrees with the resolved locale (`syncCookie` in
next-intl's middleware). A browser sending `Accept-Language: pt-BR` that lands
on `/pt-BR/…` matches neither, so no cookie is ever written and the read
silently falls back to `en-US` — the exact user most likely to notice. This
was shipped once and caught in review.

## Validation and error messages

zod schemas are factories taking a translator — see
`.claude/rules/validation.md`.

better-auth error **codes** are the contract. The server throws an English
message alongside the code; the UI renders `authErrorMessage(t, error.code)`
and never `error.message`.

Its bounded messages (`PASSWORD_TOO_SHORT`, `INVALID_NAME`,
`PASSWORD_DOES_NOT_MEET_REQUIREMENTS`) get their `{min}`/`{max}` from
`MESSAGE_VALUES` in `src/lib/auth-errors.ts` — a lookup table keyed by error
code, not a value passed at the call site like `validation.auth` above.
`MESSAGE_VALUES` is typed `Partial<Record<AuthErrorKey, …>>`, so a new bounded
key added without an entry there compiles cleanly and only fails at runtime,
as an unresolved `{placeholder}` in the rendered message. Add the map entry in
the same commit as the key.

## Testing

- Schema and error-map specs assert **keys**, using a key-echoing stub. Copy
  changes must not break them.
- Component specs render through `renderWithIntl` from `@/test-utils/intl`,
  which supplies the real English catalog — so the English copy itself stays
  under test.
- e2e specs run in `en-US` via the `path()` helper in `e2e/helpers.ts`.
  `e2e/locale.spec.ts` covers negotiation and the other two locales.
